Assignment 2 — From “It Runs in Parallel” to “I Know Why It
Doesn’t Scale”
Covers: Week 3 (OpenMP & Parallelising ML Kernels) + Week 4 (MPI for Distributed ML Sys-
tems)
Effort budget: ~3 hours total, all-inclusive (code + report)
Deliverables: 3–4 original code files you write yourself + 1 short report (PDF or Markdown, 1.5–2
pages)
T ools needed: Python 3.8+, NumPy, a C compiler with OpenMP support, and an MPI imple-
mentation (Open MPI or MPICH), plus mpi4py if you want to write Part B in Python. No GPU
required.
One-time setup (do this before you start the clock):
# macOS (Apple clang needs libomp for OpenMP):
brew install libomp open-mpi && pip install mpi4py
# Ubuntu / Debian:
sudo apt install build-essential openmpi-bin libopenmpi-dev && pip install mpi4py
# Cluster: gcc already has -fopenmp; module load openmpi
On macOS, compile OpenMP code with clang -O2 -Xpreprocessor -fopenmp -I$(brew
--prefix libomp)/include -L$(brew --prefix libomp)/lib -lomp file.c. On Linux,
use gcc -O2 -fopenmp file.c. Check that you really are running threads : print
omp_get_max_threads() at start-up. A program that compiles without OpenMP runs serially
and still prints numbers, but they are meaningless for this assignment.
Ground rule: write your own code. As in Assignment 1, you are asked to implement the
Week 3/4 concepts yourself, not to run or patch the course’s example scripts. Do not open or copy
from examples/week3_openmp/ or examples/week4_mpi/ while completing Parts A–C. Work from
the slides and the spec below. Those scripts are there to sanity-check your numbers afterward.
Reusing your own Assignment 1 code is allowed, and Part C and Part D require it.
Why this assignment
In Assignment 1, Part B, you estimated wall-clock time on 1,024 GPUs by assuming perfect
linear scaling , with a promise that Week 4 would show why that’s optimistic. This assignment
delivers on that promise.
Week 3 moved from measuring one node to programming it: threads, data scoping, races, reductions,
and tiling a GEMM so that it actually uses the cache. Week 4 went across nodes: message
passing, deadlock, collectives, the 𝛼–𝛽 cost model, ring all-reduce, and data-parallel training as
“local gradients + all-reduce” . The thread that runs through both weeks is the reduction pattern .
A reduction(+:sum) inside one node becomes an MPI_Allreduce across the cluster.
The course discipline hasn’t changed:
measure → classify → change one thing → re-measure
What’s new is that “classify” now has a third answer besides compute-bound and memory-bound:
synchronisation/communication-bound.

Part A — OpenMP: first correct, then fast (60 min)
File to submit: omp_kernels.c
Write a single C program (one main, with a command-line argument or a #define to choose the
section if you like) that does the following.
A1. Correctness: the same dot product, four ways
Compute the dot product of two double vectors of length 𝑁 = 2 24. Initialise a[i] = 1.0 and
b[i] = 0.5 so that the exact answer is 𝑁 /2 and can be represented exactly. Implement:
1. Racy: #pragma omp parallel for with a shared sum += a[i]*b[i]. This is the deliberate
bug.
2. critical: the same loop with the update inside #pragma omp critical.
3. atomic: the same loop with #pragma omp atomic.
4. reduction: #pragma omp parallel for reduction(+:sum).
For each one, print the result, its absolute error against 𝑁 /2, and the wall-clock time
(omp_get_wtime()). Run the whole program at least 3 times with OMP_NUM_THREADS set
to your core count, and record how the racy answer changes between runs. (If critical takes
more than ~10 s, you may use a smaller 𝑁 for variants 2–3 only. Say so in the report.)

A2. Speed: naive vs parallel vs tiled GEMM
Implement 𝐶 = 𝐴 ⋅ 𝐵 for 𝑁 × 𝑁 row-major double matrices (default 𝑁 = 1024 ) in three versions:
1. Naive serial: the textbook i, j, k triple loop.
2. Naive + OpenMP: the same loop with #pragma omp parallel for on the loop of your
choice. Add a one-line comment saying which loop you parallelised, and why that choice
causes no race on C.
3. Tiled + OpenMP: cache-blocked with tile size 𝑇 (default 𝑇 = 64 ), parallelised over tiles
of C.
Check versions 2 and 3 against version 1 (max absolute difference < 10 −9). Report GFLOP/s
= 2𝑁 3/𝑡. Use the Assignment 1 timing recipe: one untimed warm-up call, then average over at
least 3 timed calls. State the compiler and flags you used ( -O2 vs -O3 makes a real difference, so
the flags must be stated).

A3. Thread-scaling study

For the reduction dot product (A1.4) and the tiled GEMM (A2.3) , sweep OMP_NUM_THREADS
= 1, 2, 4, 8, … up to your machine’s logical core count ( sysctl -n hw.logicalcpu on macOS,
nproc on Linux). Write the sweep yourself, either as a shell loop or with omp_set_num_threads()

Part B — Build your own ring all-reduce (50 min)
File to submit: my_allreduce.c or my_allreduce.py (mpi4py), your choice

B1. Implement it

Write a function ring_allreduce(buf, n, comm) that sums a length- n vector of doubles across
all ranks in place , using only point-to-point calls : MPI_Sendrecv, or MPI_Isend/MPI_Irecv +
MPI_Waitall. You may not call MPI_Allreduce, MPI_Reduce, or MPI_Reduce_scatter inside it.
Use the two phases from the slides:
• Reduce-scatter: 𝑃 − 1 steps. At each step, send one chunk to rank (rank+1) % P, receive
one from (rank-1+P) % P, and add it into your copy.
• All-gather: 𝑃 − 1 steps that circulate the fully reduced chunks until every rank holds the
whole result.

Your function must work when n is not divisible by P, which the class demo does not handle.
(Hint: chunk c covers indices [c*n/P, (c+1)*n/P) with integer division.)

Correctness test: fill buf with random values (seed by rank), then compare your result with
MPI_Allreduce on a copy. Run with P = 2, 3, and 4 , and use at least one n that is not a
multiple of P. Print the max absolute difference. It should be < 10 −10, not exactly 0, because
floating-point addition is not associative and the library may add in a different order. Say this in
your report.
In one sentence in the report, explain why replacing your Sendrecv with a plain MPI_Send followed
by MPI_Recv on every rank can deadlock for large n but appear to work for small n.


B2. Measure it against the 𝛼–𝛽 model
With 𝑃 = 4 , time your ring and MPI_Allreduce for message sizes 𝑛 = 2 4, 28, 212, 216, 220, 224
doubles. Methodology: warm up, put an MPI_Barrier before each timed batch, average over many
iterations (more for small 𝑛), and report the maximum across ranks (reduce the times with
MPI_MAX). The slowest rank sets the step time.
